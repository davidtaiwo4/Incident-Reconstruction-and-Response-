# Incident-Timeline-Reconstruction-and-Response-

# Executive Summary

This project reconstructs a sealed, multi-source security incident — host process logs, PowerShell operational logs, a phishing email and a real packet capture — into a single, deterministic super-timeline, built entirely by code. A version-aware parser normalizes all four evidence types into one common schema, preserving the exact raw locator for every event, and an unattended pipeline recreates the same 100,006-row timeline from a clean checkout every time it is run.

The pipeline is validated against all 12 published fixture tests covering event classification, clock normalization, deduplication, damaged-record quarantine, and manifest-tamper detection, and separately confirmed against the real evidence itself: zero duplicate events, zero malformed timestamps, and zero network-protocol anomalies were found across all 100,000 host records and the full packet capture, after specifically checking for them rather than assuming their absence. The recovered exfiltration archive — 53,891 bytes, 5,137 records — was independently reconstructed two separate ways, once through Zeek's file-extraction framework and once through a raw packet reassembly built from nothing, and both methods agree on the exact same bytes down to the offset. One detection rule per available evidence type (Sigma for host behavior, Zeek for network C2) was written and tested against both a positive case and a constructed negative case, and containment and recovery automation was built to require explicit confirmation before changing any state.
 

During investigation, the phishing email received by an employee at NorthStar was discovered which led to a malicious document being opened on a single workstation (NS-WKS-101). Opening it triggered a PowerShell script that installed a disguised scheduled task for persistence, packaged a customer-data file into a zip archive, and uploaded that archive to an external server — the entire sequence took under a minute and was then partially cleaned up by deleting the local copy.

This matters because customer data left the organization: a 53,891-byte archive containing 5,137 customer-style records was confirmed sent to the attacker's infrastructure. This conclusion is not a single-source guess — it was independently verified two separate ways (Zeek's file-extraction engine and a raw packet reconstruction), and both agree on the exact same bytes.

The investigation also had to correct a nearly 24-hour clock error on the affected machine before any of this could be reliably ordered — verified three separate ways rather than assumed. After correction, an exhaustive search across all 100,000 activity records and all 379 machines in scope found no evidence the incident spread beyond this one host.

Two honest gaps remain: the exact malicious document that was opened was never recovered (only strong circumstantial evidence ties the email to what happened next), and no second data-integrity issue was found despite specifically looking for one. Both are stated plainly in the findings rather than glossed over.

Recommendation: treat this as a contained, single-host incident. Block the confirmed attacker domain and IP, remove the identified scheduled task, and re-image the affected machine rather than attempting manual cleanup — ready-to-run scripts for both steps are included and require explicit confirmation before making any change.

## What it is
An unattended, parser-driven super-timeline pipeline covering four evidence
types (Sysmon JSONL, PowerShell-operational JSONL, email and Zeek-derived
pcap logs), with confirmed clock correction, cross-validated exfiltration
archive recovery, tested Sigma/Zeek detection content, and dry-run-by-default
containment/recovery automation — reconstructing a single-host phishing →
persistence → staging → exfiltration incident from the sealed evidence pack.

## Exact reproduction order
All commands below run from `soc-stage9/` (root folder).
1. `make provision` — creates venv, installs pytest/scapy
2. Verify `original/evidence/` files' SHA-256 against `case-manifest.csv` before proceeding
3. `make build` — sanity-imports every pipeline module
4. `make test` — runs the full test suite; expect all tests passing (parsers, public fixtures, recovery, detections, containment)
5. `make pcap-integrity-check` — reproduces the tampered-item/anomaly check cited in incident-report.pdf; expect "no weird.log" output
6. `make timeline` — runs `timeline-builder/build_timeline.py`; expect 100,006 rows written to `timeline.csv`. Also regenerates `working/zeek-logs` automatically
7. `make recover` — runs `recovered/recover.py`; expect `recovered/case-export.zip` (SHA-256 `8e994147097a29a84a1b162cc2aaae6f5592ff135406aaca9c1668d512b98825`, 5,137 records)
8. Full clean rebuild: `make clean && make provision && make build && make test && make timeline && make recover`

## Case findings summary
See `incident-report.pdf` for full detail

- Confirmed single-host incident chain (NS-WKS-101): phishing-correlated document open → PowerShell → scheduled-task persistence → archive staging → C2 upload → local cleanup
- Clock offset confirmed: sysmon -85,609s, via 3 independent event-pair measurements (agreement within 50s)
- No lateral movement: exhaustively checked across all 100,000 sysmon records / 379 hosts
- Exfiltration archive recovered and cross-validated 2 independent ways: 53,891 bytes, SHA-256 `8e994147097a29a84a1b162cc2aaae6f5592ff135406aaca9c1668d512b98825`, 5,137 records
- No tampered item, duplicate event, or damaged record found despite exhaustive checks across all four evidence types (see decision-log.md, evidence-index.csv)
- Detections: 1 Sigma rule + 1 Zeek notice rule, each with tested positive and negative fixtures
- Containment/recovery: dry-run-by-default scripts under `response/`, scoped to the confirmed single-host impact boundary

## Known limitations
Documented in full in `incident-report.pdf` section 7. Summary:
- The literal executed initial-access artifact was not recovered — delivery is confirmed via correlation token and timing, not by recovering the malicious file's bytes
- No DNS traffic exists in `incident.pcap`; `zeek_dns` is verified only against the public fixture
- No real `.evtx` evidence exists in this pack; `PARSER-EVTX` is verified only against the public fixture
- Zeek's `uid` is non-deterministic across reruns; correlation logic re-derives it live rather than assuming a fixed value
- `remove-persistence.ps1` verified via static checks only — no Windows/pwsh runtime available in this environment
- Zeek C2 rule's negative test uses a self-constructed synthetic pcap, since no benign-comparison capture was supplied
